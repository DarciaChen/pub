# G. 給未來 session 的信

寫於 2026-07-12，Fable 5 促銷窗口最後一天，由 Fable 5 執筆。
讀者：接手的任何模型，以及三個月後回來檢視制度的 Darcia。

## 三件 Darcia 沒問、但我認為最重要的事

1. 真正的瓶頸不是模型強弱，是「真相來源分散」。
   Darcia 的關鍵規格散落在四個地方：Claude 的記憶、對話歷史、repo 檔案、她的腦中。
   四處不一致是本環境最大的錯誤來源（今天端點通關語失效就是實例——記憶裡的規格
   已與現實脫節，而沒有任何機制會發現）。制度的核心價值不是讓弱模型變聰明，
   是把真相收斂到 repo 單一位置。任何 session 發現「記憶與檔案不一致」，
   最重要的動作不是完成手上任務，是把不一致回報並修正。

2. 公開 repo 是唯一副本，這本身是風險。
   pub repo 是公開的：制度檔可以放，但通關語、token、含內部資訊的規格永遠不能放。
   同時它也是「唯一」副本——建議 Darcia 建一個私有 repo 或本機資料夾存放
   機密規格（部署憑證、含價格的內部文件），並定期把 pub repo clone 一份當備份。
   模型該做的：看到機密內容即將寫入公開檔案時，無條件攔下來問。

3. Claude Code 的 git 歷史比任何制度檔都可靠。
   Apps Script 端點是行動場景的便利通道,但單檔覆蓋、無審查。現在有了 Claude Code,
   主要工作流應該是:本機改 → commit(訊息寫清楚為什麼)→ push。commit 歷史
   就是免費的備份、教訓紀錄和回滾機制。制度檔會過時,git log 不會說謊。

## 這套制度最可能的退化方式與預防

1. 「寫了沒人讀」：制度檔存在但 session 不載入。
   預防：CLAUDE.md 放在 Claude Code 專案根目錄（自動載入）；claude.ai 靠
   Project instructions。每季由 Darcia 抽查一次：問模型「硬規則第 3 條是什麼」，
   答不出來就是載入鏈斷了。
2. 「規則通膨」：每次踩雷都加一條，兩年後 500 行沒人執行。
   預防：maintenance.md 的精簡週期是硬規定;加新規則時優先問「能不能改寫既有條目」
   而不是新增。規則數量是負債,不是資產。
3. 「型號石化」：檔案裡的模型名、參數、費率過期但被當事實引用。
   預防：所有具體型號與數值都帶日期標記,超過 6 個月自動視為【待確認】。
   model-dispatch.md 已內建此規則。
4. 「驗證儀式化」：口頭寫「已驗證」但沒真的 fetch/執行。
   預防：驗證回報必須附證據（回應碼、輸出片段、diff），不接受「已確認可用」
   這種無證據句。審查範本已含此檢查。

## 誠實清單：本次產出中我信心最低的部分

1. 「effort 參數」的存在與取值（model-dispatch.md）——僅第三方來源，
   官方文件未見，已標【待確認】。可能根本不存在或已改名。
2. Apps Script 端點規格——今天實測 UNAUTHORIZED,代表記憶中的通關語或
   端點協議已失效。CLAUDE.md 高頻任務節關於端點的描述,在 Darcia 修復前
   都是【待確認】。
3. 文案 rubric（judgment-rubrics.md C 節）——品味類判斷本質上難以外化,
   我寫的判準能擋住「明顯爛」的文案,擋不住「平庸」的文案。這是誠實條款
   說的「補不了的模糊題」:重要文案仍應升級模型或由 Darcia 定稿。
4. claude.ai 側「同對話自驗」的效力——我在 model-dispatch.md 允許它作為
   最後手段,但同上下文的自我審查有確認偏誤,效力可能比我標註的還弱。
   高風險產出不要用這條。
5. 本套制度未經任何實戰檢驗——全部產出於同一個 session、同一個模型的視角。
   前三週的使用會暴露我看不到的問題,請如實寫進 lessons.md,不要為了
   維護制度的完整性而遷就它。制度為工作服務,不是反過來。
